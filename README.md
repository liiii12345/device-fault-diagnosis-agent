# APX-240 设备故障诊断 Agent

**把设备说明书、安全红线和历史工单变成一个能在飞书里跑的现场诊断助手：它说的每一句话都带出处，说不出处的时候就说「无法判断，建议人工复核」，绝不用猜的顶替知道的。**

面向自动封装设备（APX-240）的一线操作员与维修人员。操作员在飞书群里用大白话描述现场，Agent 回一张卡片：可能原因按证据强弱排序、排查顺序照说明书抄、该停机的直接叫停、该升级的点名升级、该拒绝的违规请求当场拒绝。工单自动落表，处置完闭环，专家提交结论、报修人现场确认，两人签字后经验才沉淀进知识库，下一次同类故障的诊断就更准。

## 一、三十秒跑起来

不需要装任何第三方包，纯标准库（本机验证于 Python 3.13.5）。没有飞书凭据也能完整跑通闭环（消息落到 `var/outbox.jsonl`，工单落到 `var/work_orders.json`）。

**第一步：本地跑起来（主入口，不依赖网络与任何凭据）**

```bash

cd apx240-fde
python run.py web                            # → http://127.0.0.1:8765/
```

<https://retrieval-stowing-cascade.ngrok-free.dev>

它只在维护者这台机器开机且 `start-demo.bat` 正在跑的时候可达（域名固定不变）。首次打开若出现 ngrok 拦截页，点 "Visit Site" 即进入；返回 404 或 `ERR_NGROK_*` 就是隧道断了，**此时回到第一步本地跑**——两边是同一份代码、同一套接口，功能完全一致，不存在"在线版更完整"这种差别。

### 支持什么输入

| 输入类型 | 支持 | 说明 |
| --- | --- | --- |
| **文字**：一段中文现场故障描述 | ✅ 运行时唯一输入 | 口语化说法与中文数字都能解析（「温度只有一百五十二度」「一直报」「门关严了」）；带读数与单位更好（`152°C`、`12.4A`、`0.6MPa`） |
| **表格规则**：`knowledge/` 下 5 张 JSON 表 | ✅ 但属于搭建期输入 | 说明书在搭建阶段被结构化成 5 张表，运行时读表不读 PDF；换设备只换这 5 张表，代码零改动（§八） |
| **PDF 说明书** | ⚠️ 不在运行时读取 | 刻意不让 Agent 每次现场翻 PDF：那等于把判定交给模型的自由理解。说明书的内容已经落成表，运行时按表匹配 |
| **图片**（现场照片、报警面板截图） | ❌ 不支持 | 图像识别会把判定压在一个不可控的模型上，而这个场景最不能接受的就是不可控的判定；本仓库也不收录厂商资料原文（见 §十一），没有可供识别的图源 |
| **回填表单**：`/?wo=工单号` | ✅ 第二轮输入 | 页面按那一单的待补项出题，答完用「原描述＋你的答复」重跑同一条诊断链，另建关联工单并推第二轮卡片 |

输入的硬约束（都写进了测试，不是口头承诺）：

- 一次一条故障描述。空输入直接回「现场描述为空，无法诊断。」，不会硬编一套结论。
- 报警码可以不给。缺码时按现场征兆走 SAFE-01/SAFE-05 判定（该停机的照样停机），不会因为没有码就放行。
- 报警码给了但知识库没有（例如 A777）→ 明确回答「知识库未覆盖，无法给出有证据的可能原因」并强制升级，一个原因都不编（见 §四 样例 B）。
- 现场在描述里提出违规请求（短接安全门、带电插拔、继续试跑）→ 请求被记进「已拒绝的请求」并触发停机，而不是"提醒注意安全"。

## 二、十三个命令

两个全局开关（写在子命令之前）：`--knowledge DIR` 指定知识库目录，`--llm` 启用模型兜底解析口语化描述（需配齐 `APX240_LLM_BASE_URL` / `_API_KEY` / `_MODEL`，缺一项则提示并按纯规则版本继续）。凭据可集中写在项目根的 `.env`（自动载入，不覆盖已有环境变量），模板见 `.env.example`；飞书建应用、建群、建多维表格与六个凭据的配置步骤见本文第六节「飞书集成：DryRun 优先」。

`--llm` 默认关闭是为了「无凭据也能跑、结果可复现」；**演示统一带上它**（`start-demo.bat` 里就是 `run.py --llm web`）。它救回的是正则没枚举过的口语说法——实测同一句「A101 进料检测超时…还有股塑料烧糊的味儿」：纯规则版读不出「焦味」这条 SAFE-01 立即停机征兆，判成可继续；带 `--llm` 后模型补齐「P1 指示灯状态、焦味、物料是否到位」三个信号，判成**必须停机 + 升级专家**，代价 +2.3 秒，出处仍写 `INPUT:「还有股塑料烧糊的味儿」`（必须是现场原话的子串，回核不过就丢弃）。对照脚本就是这两条命令，差别当场可见：

```bash
python run.py diagnose "A101 进料检测超时，封口头有一股塑料烧糊的味儿，还往外冒热气。"          # 纯规则：判可继续
python run.py --llm diagnose "A101 进料检测超时，封口头有一股塑料烧糊的味儿，还往外冒热气。"    # 带兜底：立即停机 + 升级专家
```

## 三、架构：一个确定性核心，前后各一道闸门

```
   │
   ▼
① 解析层 parse.py ──────────── 正则抽取报警码、读数、征兆、违规请求
   │                            抽不到就是抽不到，标 unknown，不猜
   │                            口述中文数字（「一百五十二度」）也在这一层归一化
   ▼
①b 兜底解析 llm_parse.py ───── 正则漏掉的口语表达交给模型听写
   │                            每个字段必须附原文片段，且数值能从片段里算出来
   │                            复核不过就丢弃；正则已抽到的一律不覆盖
   ▼
② 安全门控 safety_gate.py ──── 【第一道闸门：在生成之前】
   │                            命中 SAFE-01/03 立即短路到「停机 + 升级」
   │                            不给后面的逻辑任何"权衡"的机会
   ▼
③ 证据匹配 evidence.py ─────── 历史案例逐个信号比对，四种状态：
   │                            strong_match / differs / unverified / refuted
   │                            决定性信号一旦矛盾，整条案例作废（一票否决）
   ▼
④ 诊断组装 diagnose.py ─────── 8 字段成型，每条事实挂来源标签
   │
   ▼
⑤ 输出后自检 validate.py ───── 【第二道闸门：在生成之后】
   │                            8 项逐条核对；任何一项不过 → 失效关闭
   ▼
⑥ 飞书通道 feishu/ ─────────── 发卡、写工单、看板
```

**①b 排在 ② 之前是刻意的**：模型补齐的 SAFE-01 征照样要触发强制停机。放在门控之后，
等于让口语化描述里最危险的那一类信号漏过去。

### 为什么是「两道闸门」而不是「一个好 prompt」

客户签约前一定会问一句：**「AI 乱指挥出了安全事故，谁担责？」**

这个问题不能靠在 prompt 里写「请注意安全」来回答。所以责任边界写死在代码里：

- **门控层先于一切生成执行。** 一旦现场描述里出现「冒烟」「焦味」「剧烈振动」，或者出现「短接安全门」「带电插拔」这类请求，`safety_gate.evaluate()` 直接把 `must_stop=True`、`escalate_to_expert=True` 钉死。后面的证据匹配再怎么算，也翻不了这个结论——它只能补充原因，不能撤销停机。
- **自检层在所有生成之后逐条复核，且失效关闭。** 输出里每一个数字、每一个来源标签都被反查一遍：能不能在输入原文或知识库里找到？找不到就不许发出去。自检不过时不是打个警告了事，而是 `enforce()` 精准剔除被污染的事实、**整体撤回可能原因与排查顺序**、强制 SAFE-05、改为「停止进一步排查，等待专家复核」。

一个从不失败的校验器等于没有校验器。所以 `tests/test_validate.py` 里有一半用例是**故意投毒**的：往真实诊断结果里塞进编造的 `999°C`、伪造的来源标签 `模型常识`、断言式措辞 `已确认是加热器开路`、重排过的排查顺序、违规建议 `可以短接`——每一条都必须被拦下，拦不下就是测试失败。

### 证据匹配用「四状态 + 一票否决」，不用相似度打分

传统 RAG 会算个相似度分数，0.78 就采纳。设备维保不能这么干：两个案例现象描述很像，但决定性信号相反，那就是两回事。

所以 `evidence.py` 对每个历史案例逐信号比对，给出四种明确状态，案例自带的 `critical_signal` 拥有一票否决权：

| 状态 | 含义 | 处理 |
| --- | --- | --- |
| `strong_match` | 关键信号全部一致 | 可引用其根因，证据强度按说明书定 |
| `differs` | 关键信号出现矛盾 | **该案例根因作废**，写入「已反驳」并说明差在哪 |
| `unverified` | 现场没提供足够信息 | 不采纳，转成「需要补充的信息」 |
| `refuted` | 被当前读数直接推翻 | 同 differs，且在提示里讲清为什么不引用 |

陷阱用例 T3 就是这个机制的试金石：现场报 A401「门已经关严、一直报」，历史案例 H04 的根因是「联锁安装位置松动」，但 H04 的决定性信号是「报警间歇出现」，当前现场是「一直报」——矛盾，H04 作废。Agent 会明说：不引用 H04，须按报警码顺序重新排查。

**这一条是「判断不许靠大模型常识」的正面回答：不是不让模型判断，而是让判断有可核对的依据，依据错了结论就跟着撤回。**

### 模型只当听写员，不当裁判

正则解析层是确定性核心，但它只认我枚举过的说法。现场口述千变万化——「封口头有一股塑料烧糊的味儿，还往外冒热气」——这句话里没有任何一个词命中焦味或烟雾的词表，规则层只能标 unknown，最后触发 SAFE-05 说「知识库无法覆盖」。这是这类 Agent 在真实车间里最常见的失效方式，比模型胡说更常见。

所以 `agent/llm_parse.py` 补了一层：**把「听懂话」交给模型，但模型的输出一个字段都不许直接进诊断。** 每个字段必须附带现场原文片段，并过三道复核：

1. **片段必须是现场描述的真实子串** —— 模型不能引用一句没人说过的话
2. **数值必须能从该片段里算出来** —— 阿拉伯数字或中文数字均可，算不出来就是编的
3. **规则解析已抽到的字段一律不覆盖** —— 能对上原文的正则优先于模型

复核通过才写进 `Signals`，出处仍标 `INPUT:「原文片段」`：那段话确实是现场说的，只是由模型而不是正则读出来的。输出的 `提示` 栏会列出本次由模型补齐了哪些信号，工单表里也记一列 `模型辅助解析`，`推理引擎` 一列从 `deterministic-core` 变成 `deterministic-core+llm-parse`——**谁参与了这次判断，事后查得到。**

上面那句「烧糊的味儿 + 冒热气」接上模型后，`焦味` 与 `烟雾` 被补齐，SAFE-01 立即停机征兆正确触发。同一次调用里我还故意让模型返回了一个编造的读数 `999`，配的原文片段是「我不敢靠近」——**片段是真的，但 999 算不出来，这个字段被丢弃，从未进入输出**，8 项自检照常全过。

**刻意不交给模型的三个字段：**

| 字段 | 为什么不给 |
| --- | --- |
| `alarm_code` | 把现象映射成报警码是**判断**，不是听写。判断错了整条诊断链都跟着错 |
| `user_request` | 直接触发 SAFE-03 硬拒绝。让模型决定「这句话算不算违规请求」，等于把责任边界交到模型手上 |
| `wants_continue_run` | 同上 |

反过来，SAFE-01 那几个立即停机征兆是**允许**模型补的，而且只接受 `true`。因为补出来的方向永远是「更保守」——只会触发停机升级，不会解除任何已成立的停机要求。误报一次停机损失几分钟，漏报一次冒烟损失的是一条产线。

开启方式（默认关闭，未配置时对诊断行为零影响）：

```bash
export APX240_LLM_BASE_URL="https://your-endpoint/v1"
export APX240_LLM_API_KEY="sk-..."
export APX240_LLM_MODEL="your-model"
python run.py --llm diagnose "封口头有一股塑料烧糊的味儿，还往外冒热气。"
```

三项环境变量缺任何一项，CLI 会提示并按纯规则版本继续跑——接手的人手上没有 key 是常态，兜底层缺席不该让诊断跑不起来。模型调用失败（断网、401、超时）同理：规则解析的结果照常输出，**但这条失败必须在输出的「提示」栏里显形成一句「模型兜底解析本次未生效…」**，不允许静默退回成一次看起来完全正常的纯规则诊断——那等于把一次漏判伪装成一个结论。

## 四、输出的 8 个字段

```
## 故障现象        设备报了什么码、现场可见可听的异常、现场提出的请求
## 已知事实        每条都挂来源标签，无来源的不许出现在这里
## 可能原因        按证据强弱排序（强/中/弱），标题里就写明「均为可能而非已确认」
## 证据来源        MANUAL:§n:xxx / KB:LEARNED:Lnn / INPUT:「原文片段」
## 安全前置条件    断电锁定挂牌、泄压、冷却、禁止绕过联锁、仅限授权人员
## 排查顺序        逐条抄说明书，标注每一步的执行权限
## 需要补充的信息  现场没说的、说了但没测的
## 停止条件/升级    是否停机、是否升级、升级给谁、触发哪条红线、判定理由
```

外加两个条件字段：**已拒绝的请求**（命中 SAFE-03 时出现）、**提示**（案例被反驳、证据被降级时出现）。

### 来源标签的三类

| 前缀 | 含义 | 谁维护 |
| --- | --- | --- |
| `MANUAL:§n:` | 设备厂商说明书原文（§2 安全规则 / §3 报警码 / §4 历史案例 / §5 维修记录） | 厂商，**Agent 只读，不得改写** |
| `KB:LEARNED:` | 本厂工单闭环后沉淀的现场案例：专家提交技术结论＋报修人现场确认，两人签字才入库 | 客户，可单独查看、单独回滚 |
| `INPUT:` | 现场描述原文片段 | 报修人 |

沉淀表和说明书原文**刻意分成两个文件**（`history_cases.json` vs `cases_learned.json`）。说明书属于厂商，AI 改不了也不该改；现场经验属于客户，要能被单独审计、单独撤销。混在一张表里，客户就再也说不清哪句是厂商的依据、哪句是自己攒的经验。

**现存数据的实际状态**：`cases_learned.json` 里有两条，过的是两道不同的闸门，所以输出里的写法也不同。L01（A203 加热回路接触器触点老化）沉淀于 2026-09-07，**早于双人确认这道闸门**，只有 `confirmed_by`（专家（电气）），`field_confirmed_by` 是空的——没有回头补一个签字上去，那是伪造，比承认规则升级过更糟。L02（A205 控制继电器粘连）沉淀于 2026-09-09，来源工单 `RX-20260909-0015`，是真机跑通双人确认后入的库，两个署名都在文件里，查得到就是查得到。③可能原因的「依据」栏因此按每条案例自己的署名分两种写法：有现场署名写「经专家提交、报修人现场确认，双人签字入库」，没有就如实写「早于双人确认规则、没有现场署名」。

**署名一律是角色标签、一次性确认码不留档**，这条边界怎么处理、为什么仍然可审，见 §十一。

### 自检的 8 项

`agent/validate.py` 在输出成型后逐条核对：

1. **八字段齐全** — 缺一个就不许发
2. **已知事实来源可追溯** — 每条事实的来源标签必须匹配 `MANUAL:§n` / `INPUT:` / `KB:`
3. **可能原因不含断言措辞** — 出现「已确认」「确定是」「一定是」「根因为」即失败
4. **无违规操作建议** — 全文扫描「可以短接」「建议绕过」「先继续生产」「不用停机」等
5. **排查顺序与说明书一致** — 编号必须连续，内容必须逐字对得上说明书；已触发停机时为空是合法的
6. **未覆盖时不编造** — 知识库没这个报警码，就不许给出原因和步骤
7. **数字全部可溯源** — 输出里每个数字（单位数除外，那是序号/位号）都要能在输入原文或知识库白名单里找到
8. **停机与升级判定一致** — 触发了红线、或报警码说明书属性要求升级/禁止试运行，输出就必须停机升级

第 7 项是最能兜住幻觉的一条：模型编一个 `999°C` 出来，白名单里没有，直接拦下。

### 现场必须拿到的 6 项输出 → 本 Agent 的字段

这 8 个字段不是随意切的：现场拿到一张诊断，必须能当场回答下面这 6 个问题，缺一个都不能开工。

| 现场要的答案 | 本 Agent 的哪个字段 |
| --- | --- |
| 故障现象 | **① 故障现象**：报了什么码、现场可见可听的异常、现场提出的请求 |
| 可能原因 | **③ 可能原因**：按证据强弱排序（强/中/弱），标题就写明「均为可能而非已确认」 |
| 证据来源 | **④ 证据来源**：`MANUAL:§n:xxx` / `KB:LEARNED:Lnn` / `INPUT:「原文片段」` |
| 排查顺序 | **⑥ 排查顺序**：逐条抄说明书，每一步标注执行权限（现场人员可执行 / 仅限授权人员） |
| 需要补充的信息 | **⑦ 需要补充的信息**：现场没说的、说了但没测的；卡片上有按钮可当场回填 |
| 是否升级专家 | **⑧ 停止条件 / 升级**：是否停机、是否升级、升级给谁、触发哪条红线、判定理由 |

### 这 6 项之外自加的 2 项（任何清单都没要求，是本方案加的，理由在此）

| 额外字段 | 为什么加 |
| --- | --- |
| **② 已知事实** | 把"有出处的现场读数与说明书条目"和"推断"物理分开。没有这一栏，可能原因看起来就像模型自己想出来的 |
| **⑤ 安全前置条件** | 断电锁定挂牌、泄压冷却、禁止绕过联锁、**仅限授权人员**。不写这一栏，排查顺序就会出现"让操作员去拆加热回路"这类越权建议 |

另有两个**条件性附加块**：**已拒绝的请求**（命中 SAFE-03 时出现）、**提示**（历史案例被反驳、证据被降级、答复读不出信号时出现）。

### 合规审查类 Agent 的常见字段 → 本 Agent 的对应位置

同类 Agent 常被要求给出「是否合规／具体问题／对应规则／风险等级／整改建议／无法判断原因」这组字段。本方案没有单独设一栏叫「是否合规」，而是把它拆进判定、停机要求与红线触发里——两套口径都对得上：

| 常见字段 | 在本 Agent 的哪里 |
| --- | --- |
| 是否合规 | 卡头判定（🔴 高危 / 🔵 常规）+ ⑧是否必须停机、是否升级 +「已拒绝的请求」（现场请求是否被 SAFE-03 拒绝） |
| 具体问题 | ① 故障现象 + ② 已知事实（每条挂来源） |
| 对应规则 | ④ 证据来源 + ⑧触发红线（SAFE-0x）+ ⑤ 安全前置条件 |
| 风险等级 | 卡头风险等级 + 工单表「风险等级」列（高 / 常规）+「知识库覆盖度」列（full / partial / none） |
| 整改建议 | ⑥ 排查顺序（照说明书 + 每步执行权限）+ ⑤ 安全前置条件 + ③ 可能原因（按证据强弱排序，指明先查哪个） |
| 无法判断原因 | ⑦ 需要补充的信息 + ⑧判定理由 +「提示」块；规则未覆盖时直说「知识库未覆盖，无法给出有证据的可能原因」 |

### 同一份内容的两种排版

- **飞书卡片**：判定进卡头标题，正文 ①~⑧ 与工单全文同序，**一个字段一块、块内一条明细一行、条目一条不省**（实测正文 655~2058 字、卡片 JSON 2.9~6.1 KB，真发出去的卡带真实深链为 5.0~6.4 KB，最长一行 189 字）。重点靠标题、排序与 emoji，不靠删内容。真发过的三种卡头：

  ```
  🔴 高危｜A205｜立即停机｜RX-20260908-0008          → 红卡，路由到专家群
  🔵 常规报修｜A203｜可继续排查｜RX-20260909-0010      → 蓝卡，路由到报修群
  🔵 常规报修｜A203｜可继续排查｜RX-20260909-0012｜第2轮 → 回填后的第二轮卡片
  ```

  只有红蓝两色：停机、升级专家、自检失效关闭三者任一即红卡；「知识库未覆盖」也走红卡，因为覆盖度 none 必定触发 SAFE-05 强制升级（有测试钉住，不许出现第三种颜色）。值班的人在群列表里扫一眼标题就知道这单要不要管，不用点开。
- **多维表格工单**：建单写 25 个字段，其中「诊断全文」列是同一份 `d.render()`（1500~2300 字）。网格视图会截断长文本，所以卡片底部给了「📄 打开完整工单」按钮直达那条记录。
- 命令行 `python run.py diagnose "…"` 打的是同一份全文。

## 五、数据飞轮：人在闸门上

```
报修 → 建单 → 卡片进飞书群
   │
   ├─▶ ⑦ 当场回填 → 第二轮结论（新单 + 新卡片，与原单双向关联）
   │
   ▼
现场处置 → 专家从红卡点进网页，凭一次性码提交根因/处置/复机验证
   │
   ▼
候选案例（var/candidate_cases.json）
   状态「待现场确认」——此时【不参与诊断】；橙色卡进报修群，带第二个一次性码
   │
   ▼  报修人凭码署名并确认现场事实（照做了吗／恢复了吗／复机读数），两人签字
knowledge/cases_learned.json
   状态「已提升为 L01」——从此参与诊断
   │
   ▼
下一次同类故障，多一条带出处的可能原因
```

三个刻意的设计，都是为了不让 AI 给自己发毕业证：

**1. 候选案例在现场确认前不参与诊断。**
让 AI 自己把猜测写进知识库、再拿它当证据，等于给幻觉开复利。所以专家提交只产出候选，`tests/test_feishu_loop.py` 里有一条硬断言：闭环之后立刻重新诊断同类故障，刚才填进去的那个根因**不得**出现在可能原因里。`promote()` 是唯一入口，且必须同时有专家署名与报修人现场确认。

**2. 沉淀案例的证据分量低于说明书原文。**
即使特征完全一致，`KB:LEARNED` 给出的证据强度上限也是「中」，压不过 `MANUAL` 的「强」。厂内经验必须经授权人员现场验证后才能采信，这句话写在输出的依据栏里，不是藏在代码注释里。

**3. 没有可机器比对的信号特征就不许沉淀。**
`promote()` 会检查 `match_signals`，空的直接拒绝——沉淀一条匹配不上的案例，等于往知识库里塞噪音。同理，缺报警码的工单 `close()` 时会标记「无法沉淀：缺报警码」。

`python run.py flywheel` 在临时目录里把这六步跑一遍，真实知识库不动。跑完能看到：A205 在说明书里 0 个历史案例（只能靠报警码顺序排查），双人签字入库后同类故障多出一条「中」强度的原因，出处标 `KB:LEARNED:L01`，自检依然 8/8 通过。

## 六、飞书集成：DryRun 优先

`feishu/client.py` 只用标准库 `urllib`，不引入 requests/httpx——现场演示机上装不了包也要能跑。

**没有凭据时自动落到 DryRun。** 这不是偷懒，而是一条设计约束：接手这套代码的人不该被要求先去申请一个飞书应用才能验证它。所以闭环必须能在无网络、无账号的环境下完整走通，接上凭据后同一套代码直接发真消息。

配上凭据后同一套代码直接发真消息、写真多维表格：

| 环境变量 | 用途 |
| --- | --- |
| `FEISHU_APP_ID` / `FEISHU_APP_SECRET` | 自建应用凭据（换 `tenant_access_token`） |
| `FEISHU_CHAT_ID` | 报修群 |
| `FEISHU_EXPERT_CHAT_ID` | 专家群（缺省复用报修群） |
| `FEISHU_BITABLE_APP_TOKEN` / `FEISHU_BITABLE_TABLE_ID` | 工单多维表格 |
| `APX240_WEB_BASE` | 网页入口的公网地址（可选）。与飞书凭据无关：配了卡片就出「补充信息」按钮直达该单回填页、高危单另出「填写处置结论」按钮直达双人确认页，没配就改成提示现场自己打开对应网址；DryRun 下配了照样能填 |

`Config.live` 只有同时拿到应用凭据与投递目标才为真。风险等级高的工单（停机 / 升级专家 / 自检未通过而失效关闭）投专家群、卡片标红；常规工单投报修群、卡片标蓝。

**卡片与工单是两层，两层都数得齐字段。** 一次诊断对外承诺的 6 项（故障现象、可能原因、证据来源、排查顺序、需要补充的信息、是否升级专家）加上本方案自加的 2 项（已知事实、安全前置条件），共 8 项，字段对照见 §四。卡片按 ①~⑧ 排布、与全文同序，**一个字段一块，块内一条明细一行，一条都不省**——概览把内容删掉一部分，看的人还得再去别处找回来，那就不叫概览了。实测正文 655~2058 字（知识库未覆盖的单最短、A203 常规单最长）、卡片 JSON 本地重放 2.9~6.1 KB、真发出去的卡带真实深链 5.0~6.4 KB（离飞书上限还很远），最长一行 189 字，超一行就超一行，折行是飞书自己的事。判定另外写进卡头标题（`🔴 高危｜A205｜立即停机｜RX-…`），群列表里扫一眼就知道这单要不要管；突出重点靠标题、排序与 emoji，不靠砍内容。

完整 8 字段与逐条出处在工单的「诊断全文」列（`d.render()`），命令行 `diagnose` 打的也是同一份全文。卡片底部按钮：「📄 打开完整工单」直达那条多维表格记录，「✍️ 补充信息，重出诊断」直达这一单的回填页，升级到专家的单另带一个「🧑‍🔧 填写处置结论」按钮、网址里带一次性专家码。拿不到真链接就不渲染——死链比没链更糟：DryRun 下没有真 `record_id`，未配 `APX240_WEB_BASE` 或 ⑦ 已空时没有回填页可去。

**⑦ 是可以当场填的，填完就出第二轮完整结论。** 按钮指向 `/?wo=工单号`，页面从工单存档里读出原描述与待补项，一项一个输入框；提交后把原描述与补充合成一段，重跑同一条诊断链（安全闸门、四状态证据、8 项自检一项不少，第二轮照样可能停机升级），另建一张关联工单并推第 2 轮卡片。第三轮以上同样成立：`关联工单` 指回上一轮、`后续工单` 指向下一轮，两个方向分开存，链条不会在第三轮被覆盖成只能单向往后走。

答案分三类分别对待：解析层读得出信号的（「加热电流 12.4A」「今早 8 点 20 分」）直接进证据链；答了内容但没有对应信号的（「继电器触点发黑」）从 ⑦ 摘掉、在「提示」里写明本轮未据此调整证据强度；答的是「没测」「不知道」的，这一项仍然缺，留在 ⑦ 里下一轮接着问。⑦ 空的时候卡片会说清是哪一种空——「说明书要求的观测项现场都已给出」与「本轮答复的某几项读不出可判定信号」是两回事，混为一谈等于告诉现场不必再测。

回填走的是自己的网页入口，不是飞书卡片回调：回调要配事件订阅与公网回调校验，演示机上多两个活动部件；网页入口用的是同一条诊断链，且不依赖飞书凭据——DryRun 下照样能填、能出第二轮。

**经验入库走双人确认，不需要运维当 curator。** 专家从红卡点进 `/?wo=工单号&k=专家码`，填署名、实际根因、处置动作、复机验证，产出**候选**案例（不参与诊断）；橙色卡进报修群，带第二个一次性码，报修人点进去先署自己的名（这一笔就是 `field_confirmed_by`），再回答现场看得见的事——照做了吗、恢复了吗、复机读数、有无不符，**根因对不对由专家署名负责，不问他技术判断**。两个是/否题都答「是」且给了复机读数才入库，`confirmed_by` 与 `field_confirmed_by` 两个署名分开存；任何一问答「否」（或读数留空）就走退回，知识库一个字不写，而且**退回必须写清现场实际情况**——不写服务端直接拦下，否则专家不知道该改什么。退回时分歧记在工单上、红卡退回专家群并换发一个新的专家码，专家改完再走一遍。读数是否与专家结论相符由报修人判断，系统不替他比对。题目、控件类型、必填与否全部由服务端下发，页面报上来的 stage 不作数——页面一旦能自己改题目，「现场确认不问技术判断」就成了空话。说清楚它的边界：**一次性码不是身份认证**，它只证明「这个人拿得到群里那张卡」，转发链接等于转交这一步的权限；生产形态应换成飞书事件回调带 `open_id`。

`lark_md` 不认 `##` 标题与 `---` 分隔线，也不支持调字号，层级只能靠一行一个 div + 加粗 + 行内代码 + emoji 做。多维表格的网格视图会截断长文本，「诊断全文」是第 16 列，要点开记录才看得到全貌。

建单时写 25 个字段，除了诊断结论还包括 `AI调用次数`、`输出自检`、`推理引擎`、`模型辅助解析`、`提取信号`（闭环时用它构造可机器复用的案例特征），以及回填闭环要用的 `需补充信息项`（JSON 数组，回填页按它出题）、`诊断轮次`、`关联工单`、`后续工单`、`推送状态`（卡片没送达时把原因写在这里，不把通知失败说成已推送）。双人确认各阶段往同一条记录上追加：专家提交写 `实际根因`、`处置动作`、`复机验证`、`确认专家`、`闭环时间`、`候选案例` 并挂一次性 `专家码`／`现场码`；报修人确认写 `现场确认人`、`现场确认时间`、`现场确认`、不符时写 `现场分歧`；入库后再写 `沉淀状态`、`案例编号`——一张表看得到一单从报修到沉淀的全过程。

## 八、换设备只换 5 张表

这是「方案可复制到同行业其他客户」的技术兑现。`knowledge/` 下共 6 个 JSON：**5 张设备知识表**加 1 张现场沉淀表，换设备要换的是前面那 5 张：

| 文件 | 内容 | 条数 | 在输出里的体现 |
| --- | --- | --- | --- |
| `device_params.json` | 设备型号、7 个模块、正常参数区间 | 5 组参数 | 参数越界判定（例：热封稳定范围上限 170°C） |
| `alarm_codes.json` | 报警码 → 含义、常见原因（带成立条件）、安全排查顺序、强制属性 | 7 个码 | ①故障现象、③可能原因、⑥排查顺序、是否停机 |
| `safety_rules.json` | SAFE-01 ~ SAFE-05 安全红线 + Agent 安全职责 | 5 条红线 | ⑤安全前置条件、⑧触发红线、已拒绝的请求 |
| `history_cases.json` | 说明书 §4 历史案例，每条带 `critical_signal` 决定性信号 | 5 例 | ②已知事实里的逐条比对；决定性证据矛盾则该案例作废、不许引用其根因 |
| `maintenance_records.json` | §5 维修记录（历史工单）+ 使用约束 | 5 单 / 3 约束 | ②已知事实里的候选证据（明确写"不能据此断言当前根因相同"） |
| `cases_learned.json` | 工单闭环后经**专家提交＋报修人现场确认双人签字**沉淀的案例 | 现有 2 条（L01、L02） | ③可能原因里出处标 `KB:LEARNED:L01`／`L02`，证据强度上限「中」 |

前 5 张是设备资料的结构化产物（随设备更换），第 6 张是客户自己攒的经验（随工单增长）——**这两类必须分文件**，理由见 §四 与 §十一。

**代码里没有一行写死 APX-240 的知识。**

### 复制 SOP：从拿到说明书到能上线

1. **填 5 张表**（唯一的人工环节，一份说明书约半天到一天）。结构照抄现有文件即可，不要新造字段。
2. **看覆盖**：`python run.py --knowledge knowledge_新设备 knowledge`。输出会列出每个报警码的常见原因数、排查步数、关联案例数、关联工单数。哪一码是 0 关联，说明书里本来就没有——上线后 Agent 对这些码只能给 `partial`/`none` 覆盖的输出，这是要提前跟客户讲清楚的预期，不是 bug。
3. **照新说明书重写标注语料**。这一步不能省：把 `evaluation.py` 里的 `CORPUS` 换成新设备的用例，**标注照说明书填，不照代码输出填**。这是唯一能证明「换表之后判定行为仍然正确」的东西；只跑 `demo` 看输出像不像话，是看不出容差判错、红线漏判这类问题的。
4. **过门禁**：`python run.py --knowledge knowledge_新设备 eval` 退出码必须是 0（26 条标注全中 + 4 种投毒全兜住），再跑 `demo` 确认门控与失效关闭行为不变。退出码非 0 就别上线。
5. **飞书侧换群 ID 与多维表格 token，先用 DryRun 跑完整闭环**（建单 → 专家提交 → 报修人现场确认 → 案例沉淀），确认落盘内容正确再开真发。

不需要改 `agent/` 或 `feishu/` 下任何一行代码。

### 扩容路径：单台 → 车间 → 产线 → 全厂 → 集团

关键事实是：**5 张表是按「型号」组织的，不是按「台」**。所以规模往上走时，知识表的数量不随设备台数增长，只随型号数增长。

| 台阶 | 要改什么 | 不改什么 |
| --- | --- | --- |
| **单台设备（试点）** | 填 5 张表、建一个飞书群 | — |
| **同型号车间（20 台）** | 只改群 ID 与多维表格 token | 一个知识库目录、一套代码，20 台共用 |
| **混型号产线** | 每个新型号填 5 张表 + 一层「按设备选知识库目录」的分发 | `agent/` 与 `feishu/` 全部代码 |
| **全厂** | 沉淀案例按型号合并、标注来源产线 | 厂商给的那 4 张表（全厂一份） |
| **集团多工厂** | `maintenance_records` 与 `cases_learned` 按厂分开存 | `device_params`/`alarm_codes`/`history_cases`/`safety_rules` 全集团一份 |

三级往上各自的经济含义，数字都在 `EVAL.md` 里（A 节实测，B 节假设）：

- **单台试点在保守假设下一年回不了本**：实测 17.7 单/台/年，5 万投入按保守档要 5.6 年摊平。所以这门生意不能按「给一台设备卖个工具」谈。
- **车间级才是飞轮开始转的地方**：20 台同型号一年约 **212 个候选案例**（按实测闭环率 60% 推算），说明书原文只有 5 条。知识库厚度随工单数线性增长，而代码零改动——这是同一份投入越用越值钱的部分。
- **产线以上的边际成本主要是人工填表**：每加一个型号 = 重做一遍上面 5 步 SOP，不是加一轮开发。集团多工厂时，厂商知识与客户现场经验天然分表存放，所有权边界是清的（说明书属于设备厂商，AI 改不了；`cases_learned.json` 属于客户，可单独查看、单独撤销）。

双人签字这道闸门在任何一级都不能省。取消它，飞轮就会把误判一起放大——沉淀一条错案例，后面所有相似报修都会被它带偏。

### 这条路上唯一还没写的代码

**多型号路由。** `KnowledgeBase` 是「一个目录一个型号」，`Paths` 又把 `knowledge/` 与 `var/` 绑在同一个 `root` 上——所以同型号横向复制（车间、整条产线都是同一台 APX-240 的情况）今天就能直接跑，混型号需要在外层加一个按设备编号选知识库目录的分发，几十行量级。没有预先写它的原因：本方案面对的是单一型号场景，先铺一层用不上的抽象，只会让读代码的人分不清哪部分是验证过的、哪部分是设想的。宁可留一个明确的缺口，也不要一个没被验证过的抽象。

## 十、边界与诚实声明

说清楚它不做什么，比说它做什么更要紧：

- **它不替代授权人员。** 涉及线路、加热回路、伺服、气路拆装的环节，输出里逐条标注「仅限授权人员执行」，Agent 只负责把这条边界讲清楚。
- **它不下确定性结论。** 「可能原因」这个标题是刻意的，输出里出现「已确认」「一定是」会被自检第 3 项直接判失败。
- **知识库没覆盖时它就说没覆盖。** 报警码不在表里 → 覆盖度 `none` → 触发 SAFE-05 → 停止排查、升级专家、列出需要补充的信息。不会用常识编一套流程出来。
- **解析层认不出所有说法。** 正则只覆盖枚举过的表达，中文数字（「一百五十二度」）也已归一化；仍然漏掉的口语表达由模型兜底层补，但该层默认关闭，且补齐的每个字段都要过原文片段复核。两层都没读出来时，相关字段标 `unknown` 并进入「需要补充的信息」——不会猜一个值填上。
- **237 个测试只能证明「写过的用例不出错」。** 证明不了「上线后每一次输出都不出错」——所以才需要第 ⑤ 层自检在每次输出后实时核对。测试是开发期的网，自检是运行期的网，两张网都得有。

### 六条自设约束，每条配一个当场能验的动作

| 约束（本方案自设，不是别人给的清单） | 怎么满足 | 当场怎么验（一个动作） |
| --- | --- | --- |
| 使用者要能当场打开就用，不是只看别人的命令行截图 | 本地 `run.py web` 与公网链接是同一份代码；发布前先起服务自测一次 | clone 下来 `python run.py web`，点首屏一键样例 |
| 要接住现场实际会给的输入 | 现场只会给一段**文字**（故障描述），所以入口是网页文本框 + 一键样例 + 回填表单；图片不在本方案范围内（见 §一） | 把样例 A 那句粘进去，或用你自己的话描述一条 |
| 输出要结构清晰，不能是一段泛泛而谈的文字 | 8 字段固定顺序，每条事实挂来源标签，可能原因按证据强弱排序并写明"均为可能而非已确认"，卡片一个字段一块 | 看样例 A 输出的 ②③④ 三块 |
| 判断依据必须来自设备资料与安全红线，不是模型常识 | 说明书落成 5 张表；判定在生成前由安全门控钉死；证据四状态 + 一票否决；输出后 8 项自检，不过则失效关闭；模型只当听写员且产出须回核现场原话 | 看样例 A 里 H04 被反驳作废那一条 |
| 信息不足或规则没覆盖时，要明说"无法判断"并交人工复核 | 分三种情形，都不是靠模型自觉：**规则未覆盖**（码不在表里，或既无码也无可识别征兆）→ 覆盖度 `none` → 样例 B 那样直说「无法给出有证据的可能原因」并按 SAFE-05 停机升级；**无码但有 SAFE-01 立即停机征兆** → 覆盖度 `partial`，照样停机升级，不会因为"没码"就放行（`EVAL.md` A3~A6）；**码在表里但读数不全** → 覆盖度 `full`，⑦ 逐项列出待补信息，缺关键观测的那条原因降为「弱」并写明"仍需补齐"（样例 C 第一轮就是这样）。图片模糊/遮挡不适用——本 Agent 不接收图片 | 跑样例 B；再跑一句只给报警码不给读数的描述，看 ⑦ 与证据强度变化 |
| 交付必须自带跑得起来的兜底，接手的人跑不起来就等于没交付 | 四重兜底：本地起服务 → 公网隧道 → 无凭据 DryRun 跑完整闭环 → `EVAL.md` 可重跑对数；另有 237 个测试与 `run.py demo` 当场复现判定行为 | 把 `.env` 改名让凭据读不到，再跑一遍完整闭环，看是否仍然出卡片与工单 |

## 十一、这个仓库的边界

**说明书原文不在这里，也不该在这里。** 设备资料属于设备厂商，本仓库只放它的**结构化产物**：`knowledge/` 下那 5 张表把一台 APX-240 的报警码、安全红线、历史案例、维修记录与参数区间落成了机器可比对的字段。字段名（`trigger_kind`、`critical_signal`、`applies_to_steps_containing`）、关键词表、四状态证据模型都是本方案自定的工程选择，不是原文摘录。输出里的出处标签 `MANUAL:§3:A401` 指向的是**那套厂商资料的分节编号**，本仓库里没有对应的文件可以点开对照——所以要完整复核某一条判断，前提是手上那份说明书。换个角度看这正是设计的核心：Agent 依赖的是这张**知识接口**，APX-240 只是填进去的第一份实现（§八）。

**演示数据是真跑出来的。** `var/` 下 18 张工单、28 条操作日志、飞书投递记录，都是闭环实机运行的产物，不是为文档编的样例。愿意的话把它们全删了再跑一遍，程序会重新长出一套同样的结构。

**隐私处理。** 工单存档与沉淀案例里的署名一律是角色标签——`专家（电气）`、`报修人（现场）`，一次性确认码全部置空。这条边界仍然可审，靠的是字段结构而不是名字：`confirmed_by` 与 `field_confirmed_by` 是否都在、分别出自哪一道闸门（专家码那道还是现场码那道），在 `var/work_orders.json` 与 `var/work_order_log.jsonl` 里逐单对得上。**少一个签字就不入库**这条规则是否被绕过，与署名具体是谁无关，所以换成角色标签不削弱可审计性。

**没有许可证文件。** 本仓库目前不带 LICENSE。代码你可以按自己的需要取用，但请注意：`knowledge/` 那 5 张表脱胎于厂商设备资料，复用之前先确认你对原始资料的授权范围；`cases_learned.json` 属于产生它的客户现场，不是一个可以对外分发的公共数据集。

**`.env` 永远不进仓库。** 里面有飞书自建应用的 `APP_SECRET` 与模型端点的 key，`run.py` 靠它们发真消息、写真表。`.gitignore` 已忽略它，但手工压缩不会——少了这个文件接收方照样能跑（自动回 DryRun），所以没有任何理由把它带上。第一节那条 ngrok 链接同理：它只是隧道，指向的服务不保证在线，**别把它当成一个可用的线上部署**。
